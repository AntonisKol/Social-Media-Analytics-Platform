# Presentation Guide: Social Media Analytics Platform

## 1. Short opening

The project acts like a small social media monitoring system for a marketing agency. It watches fake live posts, finds hashtags, adds the user's city, measures whether posts sound positive or negative, and creates reports about which topics and users are most active.

**Technical version**

The system simulates a streaming data pipeline: a Flask API produces JSON posts, Apache NiFi validates and enriches them, Kafka stores them as a durable event log, Spark Streaming performs near-real-time sentiment aggregation in 2-minute windows, and Spark Batch reads the full history to generate daily engagement reports.

> "The same stream of posts feeds two different needs: Spark Streaming gives immediate trend visibility, and Spark Batch creates summary reports for later business decisions."

---

## 2. What each part does

| Part | Non-technical explanation | Technical explanation | File |
| --- | --- | --- | --- |
| Mock Social API | A fake social media app that produces one post per request. | Flask `GET /posts` returns a JSON record with `post_id`, `user_id`, `text`, `timestamp`, `likes`, and `retweets`. Runs in Docker on port 5000. | `simulator/simulator.py` |
| NiFi | The data collector, validator, and organizer. | Polls the API every 5 seconds, validates required fields, extracts hashtags with regex, resolves `user_id` to a city, rebuilds the JSON, and publishes enriched messages to Kafka. | `nifi/social_media_flow.json` |
| Kafka | The message waiting room. | Durable event topic `social_posts_raw`. Retains all messages so streaming and batch jobs can read independently without affecting each other. | `infra/docker-compose.yml` |
| Spark Streaming | The live trend monitor. | Reads Kafka continuously, classifies sentiment with TextBlob, groups by hashtag and city in 2-minute windows, writes results to console and Parquet files. | `spark/streaming/sentiment_streaming.py` |
| Spark Batch | The report generator. | Reads the full Kafka history once, calculates top hashtags, most active users, average engagement, and post counts by city. Saves CSV reports and PNG charts. | `spark/batch/batch_analysis.py` |
| Shared module | Common definitions used by both Spark jobs. | `HASHTAG_PATTERN` and `post_schema` defined once and imported by both jobs and the tests. | `spark/shared.py` |
| Tests | A quick confidence check. | Pytest validates sentiment labels, simulator post schema, sample data size and uniqueness, field types, and hashtag extraction. | `tests/test_pipeline.py` |

## 3. Demo script

### Step 1: Activate the environment and start the platform

> "Before anything runs, I activate the Python environment and start all services with a single Docker Compose command."

```bash
source .venv/bin/activate

docker compose -f infra/docker-compose.yml up -d --build
docker compose -f infra/docker-compose.yml ps
```

This starts six containers: Zookeeper, Kafka, a Kafka init job that creates the topic, Apache NiFi, a Spark master, and a Spark worker.

### Step 3: Show NiFi

> "NiFi is where the raw post becomes a clean, enriched event. It runs automatically every 5 seconds without any manual intervention."

Open NiFi at:

```
http://localhost:8080/nifi
```

Login: `admin` / `adminpassword`

NiFi runs a **7-step pipeline** on a 5-second timer:

**Step 1 — Poll Mock Social API (`InvokeHTTP`)**
Makes a `GET` request to `http://simulator:5000/posts` every 5 seconds. The response body becomes a NiFi FlowFile — an internal message object.

**Step 2 — Extract JSON Fields (`EvaluateJsonPath`)**
Parses the JSON and pulls `post_id`, `user_id`, `text`, `timestamp`, `likes`, and `retweets` out as FlowFile attributes — think of them as sticky notes attached to the message.

**Step 3 — Validate Post (`RouteOnAttribute`)**
Acts as a data quality gate. Posts with all required fields go down the main path (`matched`). Posts with missing or malformed fields are routed to a separate error topic (`unmatched`) — they never reach the main Kafka stream.

**Step 4 — Extract Hashtags (`ExtractText`)**
Runs the regex `((?:#\w+\s*)+)` against the post text and captures all hashtags as a single `hashtags` attribute (e.g. `#AI #MachineLearning`).

**Step 5 — Enrich with Location (`UpdateAttribute`)**
Resolves `user_id` to a city using a hardcoded lookup chain — the NiFi equivalent of a dictionary. For example `U001 → Athens`, `U007 → Amsterdam`, `U012 → Oslo`. In a real system this would be a database query.

**Step 6 — Rebuild Enriched JSON (`ReplaceText`)**
Rewrites the FlowFile content as a new JSON string that includes all original fields plus `location` and `hashtags`. This is the step that makes the enriched data available to Kafka — attributes only live inside NiFi, so they must be written into the message body here.

**Step 7 — Publish to Kafka (`PublishKafka`)**
Sends the enriched JSON to the `social_posts_raw` topic. Invalid posts from Step 3 go to a separate `PublishKafka_error` processor so bad records are isolated, not silently dropped.

### Step 6: Run live sentiment analysis

> "Now Spark connects to Kafka and starts processing the stream. Every 20 seconds it shows a table of sentiment counts grouped by hashtag and city. The job runs inside the Docker cluster so both the driver and the worker reach Kafka on the internal network."

```bash
rm -rf spark/streaming/checkpoint spark/streaming/output

docker exec \
  -e KAFKA_BOOTSTRAP_SERVERS=kafka:9092 \
  -e KAFKA_TOPIC=social_posts_raw \
  -e STREAMING_OUTPUT_DIR=/opt/spark-jobs/streaming/output \
  -e STREAMING_CHECKPOINT_DIR=/opt/spark-jobs/streaming/checkpoint \
  -e STREAMING_TRIGGER_INTERVAL="20 seconds" \
  spark-master \
  /opt/spark/bin/spark-submit \
    --master spark://spark-master:7077 \
    --conf spark.jars.ivy=/tmp/.ivy2 \
    --packages org.apache.spark:spark-sql-kafka-0-10_2.12:3.5.1 \
    --py-files /opt/spark-jobs/shared.py \
    /opt/spark-jobs/streaming/sentiment_streaming.py
```

The 20-second trigger and the 2-minute window are two different things:

- **Trigger (20 sec):** how often Spark wakes up and processes new Kafka messages. The job runs forever — it does not stop after 2 minutes. Every 20 seconds it reads what is new, classifies sentiment, and refreshes the console table.
- **Window (2 min):** how events are grouped. All posts that arrive between 10:00 and 10:02 belong to the same window bucket. Posts between 10:02 and 10:04 belong to the next bucket.

TextBlob reads each post's text and scores the polarity: above 0.1 is `positive`, below -0.1 is `negative`, everything in between is `neutral`.

Results are also written to `spark/streaming/output/` as Parquet files.

### Step 7: Run batch engagement reports

> "The same Kafka data feeds a separate batch job. This one reads the entire history and produces a daily report — top hashtags, most active users, engagement averages, and post counts by city."

```bash
docker exec \
  -e KAFKA_BOOTSTRAP_SERVERS=kafka:9092 \
  -e KAFKA_TOPIC=social_posts_raw \
  -e BATCH_OUTPUT_DIR=/opt/spark-jobs/batch/output \
  spark-master \
  /opt/spark/bin/spark-submit \
    --master spark://spark-master:7077 \
    --conf spark.jars.ivy=/tmp/.ivy2 \
    --packages org.apache.spark:spark-sql-kafka-0-10_2.12:3.5.1 \
    --py-files /opt/spark-jobs/shared.py \
    /opt/spark-jobs/batch/batch_analysis.py
```

Generated files in `spark/batch/output/YYYY-MM-DD/`:

| File | What it shows |
| --- | --- |
| `top_hashtags/` + `.png` | Top 10 hashtags by post count |
| `active_users/` + `.png` | Top 10 most active users by post count |
| `engagement_by_hashtag/` + `.png` | Top 10 hashtags by average likes + retweets |
| `posts_by_location/` + `.png` | Post count and average engagement per city |

> "Every time you run this job it reads everything in Kafka and produces a fresh dated folder. Run it tomorrow and you get tomorrow's report."

## 5. Technical talking points

- **Why Kafka?** It decouples producers and consumers. NiFi publishes once; streaming and batch jobs read independently without affecting each other.
- **Why NiFi?** It provides a visual, configurable ingestion layer with validation and enrichment before data reaches Kafka. Bad records never pollute the main stream.
- **Why ReplaceText in NiFi?** NiFi enrichment lives in flow attributes — not in the message body. ReplaceText is the step that writes all enriched fields into the JSON so Spark can read them from Kafka.
- **Why Spark Streaming?** It handles continuous unbounded data and groups events into time windows for near-real-time aggregation.
- **Why Spark Batch?** It is more efficient for summary reports that scan all historical data at once.
- **Why TextBlob?** It is lightweight and simple to explain. Production systems would use a trained model, but TextBlob is the right trade-off for a demo.
- **Why `spark/shared.py`?** `HASHTAG_PATTERN` and `post_schema` are used by both Spark jobs. A shared module means one change updates both jobs — no risk of the two drifting apart.
- **Why a Spark master and worker in the cluster?** `spark-master` coordinates job scheduling and exposes the cluster at `spark://spark-master:7077`. `spark-worker` registers with it and executes the actual tasks. Running `spark-submit --master spark://spark-master:7077` inside Docker means both the driver and the executors live on the same network as Kafka, so there is no need to expose Kafka externally. In a production environment you would add more workers to scale throughput.
- **Why Docker Compose?** It makes the entire demo reproducible with one command. Anyone can clone the repo and run it.
